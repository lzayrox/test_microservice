Microservicios

  • Servicios pequeños e independientes
  • Comunicación por APIs REST o mensajería
  • Escalabilidad horizontal
  • Base de datos independiente por servicio

Ventajas y Retos

Ventajas: Escalabilidad, menor acoplamiento, despliegue ágil

Retos: Comunicación compleja, monitoreo, transacciones distribuidas

CI/CD

Integración Continua (CI): pruebas automáticas en cada commit.

Despliegue Continuo (CD): entrega automática en ambientes.

Herramientas: GitHub Actions, GitLab CI, Jenkins, Azure DevOps.

Spring Boot

  • Framework de Java para construir microservicios.
  • Incluye servidor embebido (Tomcat/Jetty).

Importancia: productividad, escalabilidad y ecosistema robusto.

Node.js

  • Entorno de ejecución de JavaScript en servidor.
  • Basado en event loop y I/O no bloqueante.
  • Ideal para aplicaciones en tiempo real y APIs ligeras.

Opciones de Almacenamiento

  • BD transaccionales (SQL): integridad, ACID. Ej: PostgreSQL, MySQL
  • NoSQL: flexibilidad, escalabilidad. Ej: MongoDB, Cassandra
  • Data Warehouses: análisis y BI. Ej: Snowflake, BigQuery

  • Apache HTTP: servidor web modular y flexible.
  • Tomcat: servidor de aplicaciones Java EE ligero.
  • Nginx: proxy inverso, alta concurrencia y balanceo.

API Manager

  • Centraliza, publica y protege APIs.
  • Gestiona autenticación, cuotas y versiones.
  • Ejemplos: Apigee, Kong, WSO2.

  • Proveedores: HAProxy, Nginx, AWS ELB, Azure LB, GCP LB.

1) DDD + Contratos

  • Identifica bounded contexts y separa modelos por servicio.
  • Define APIs con OpenAPI, versiona (/v1), y usa contract tests.

¿Qué es DDD?

Domain-Driven Design es una forma de diseñar software que pone el negocio en el centro.

  • Se enfoca en el dominio (reglas del negocio).
  • Usa un lenguaje común entre negocio y técnicos.
  • Divide el sistema en Bounded Contexts.

Conceptos clave

  • Dominio: el problema que el software resuelve.
  • Lenguaje ubicuo: palabras claras y compartidas.
  • Bounded Context: límite donde un modelo es válido.

Bounded Context (BC)

Un BC es un límite claro donde un modelo de dominio aplica de manera consistente.

  • Cada BC tiene su propio modelo y lógica.
  • Comunican entre sí vía APIs o eventos.
  • Ejemplo: "Orders", "Payments", "Shipping".

¿Qué es un Context Map?

Es un mapa visual que muestra:

  • Los Bounded Contexts (cajitas).
  • Sus relaciones y dependencias.
  • Cómo se comunican (APIs, eventos).

¿Qué es Contract-First?

Es un enfoque donde primero se define el contrato de la API (ej. OpenAPI, AsyncAPI, GraphQL SDL) antes de escribir código.

Contract-First vs Code-First

Contract-First Code-First
Contrato se diseña primero Código se escribe primero
Equipos acuerdan el contrato antes Contrato se genera del código
Mejor comunicación entre equipos Rápido para prototipos

Ejemplo OpenAPI (YAML)


openapi: 3.0.1
info:
  title: Orders API
  version: 1.0.0
paths:
  /orders:
    post:
      summary: Crear pedido
      requestBody:
        required: true
        content:
          application/json:
            schema:
              $ref: '#/components/schemas/Order'
      responses:
        '201':
          description: Pedido creado
components:
  schemas:
    Order:
      type: object
      properties:
        id:
          type: string
        total:
          type: number
        items:
          type: array
          items:
            type: string

Beneficios

  • Lenguaje común entre equipos.
  • APIs diseñadas de forma clara y consistente.
  • Facilita pruebas automáticas (mock servers, validators).
  • Permite generar código cliente y servidor.

Herramientas útiles

  • OpenAPI → REST APIs.
  • AsyncAPI → eventos/mensajería.
  • GraphQL SDL → contratos GraphQL.
  • Codegen: Swagger Codegen, OpenAPI Generator.
  • Mock servers: Prism, Postman, Stoplight.

Resumen

  • Primero el contrato, luego el código.
  • Mejor alineación entre negocio y tecnología.
  • Ideal cuando hay múltiples equipos y dependencias.

Contract-First = APIs más claras y confiables

2) Skeleton: Node.js (Express)

// app.js
// Minimal REST service with health checks
const express = require("express");
const app = express();
app.use(express.json());

app.get("/health", (_req, res) => res.status(200).json({ status: "ok" }));
app.get("/v1/orders/:id", (req, res) => {
  // TODO: fetch order by id (repository)
  res.json({ id: req.params.id, status: "CREATED" });

const port = process.env.PORT || 8080;
app.listen(port, () => console.log(`Orders up on :${port}`));
# Dockerfile (Node)
FROM node:20-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci --only=production
COPY . .
EXPOSE 8080
CMD ["node", "app.js"]

5) CI/CD (GitHub Actions ejemplo)

# .github/workflows/ci-cd.yml (extract)
name: ci-cd
on: [push]
jobs:
  build-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20 }
      - run: npm ci && npm test
  docker-publish:
    needs: build-test
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: docker/login-action@v3
        with: { registry: ghcr.io, username: ${{ github.actor }}, password: ${{ secrets.GITHUB_TOKEN }} }
      - uses: docker/build-push-action@v6
        with:
          context: .
          push: true
          tags: ghcr.io/org/orders:sha-${{ github.sha }}
  deploy:
    needs: docker-publish
    runs-on: ubuntu-latest
    steps:
      - uses: azure/setup-kubectl@v4
      - run: kubectl apply -f k8s/

6) Kubernetes: Deploy & Service

# k8s/deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata: { name: orders }
spec:
  replicas: 3
  selector: { matchLabels: { app: orders } }
  template:
    metadata: { labels: { app: orders } }
    spec:
      containers:
        - name: orders
          image: ghcr.io/org/orders:sha-ABC123
          ports: [{ containerPort: 8080 }]
          env:
            - { name: NODE_ENV, value: "production" }
          readinessProbe: { httpGet: { path: /health, port: 8080 }, initialDelaySeconds: 3 }
          livenessProbe: { httpGet: { path: /health, port: 8080 }, initialDelaySeconds: 10 }
---
apiVersion: v1
kind: Service
metadata: { name: orders }
spec:
  selector: { app: orders }
  ports:
    - { name: http, port: 80, targetPort: 8080 }
# k8s/ingress.yaml (Nginx Ingress)
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: api
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /$1
spec:
  rules:
    - host: api.example.com
      http:
        paths:
          - path: /orders/?(.*)
            pathType: Prefix
            backend:
              service:
                name: orders
                port: { number: 80 }

7) Malla de Servicios (Istio)

  • mTLS, retries, circuit breaking, telemetría sin cambiar el código.
  • Sidecar proxy (Envoy) en cada pod + control plane.
# DestinationRule + VirtualService (retries)
apiVersion: networking.istio.io/v1beta1
kind: DestinationRule
metadata: { name: orders }
spec:
  host: orders
  trafficPolicy:
    connectionPool: { tcp: { maxConnections: 100 } }
    outlierDetection: { consecutive5xxErrors: 3, interval: 5s, baseEjectionTime: 30s }
---
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata: { name: orders }
spec:
  hosts: ["orders"]
  http:
    - retries: { attempts: 3, perTryTimeout: 2s }
      route:
        - destination: { host: orders, subset: v1 }

11) Escalabilidad & Despliegues

  • HPA por CPU/RAM/QPS; PodDisruptionBudget.
  • Estrategias: Rolling, Blue/Green, Canary (con Istio/K8s).
# Horizontal Pod Autoscaler (extract)
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: orders }
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: orders }
  minReplicas: 3
  maxReplicas: 10
  metrics:
    - type: Resource
      resource: { name: cpu, target: { type: Utilization, averageUtilization: 70 } }

12) Checklist de producción

  • SLOs/SLIs definidos (latencia, error rate, uptime)
  • Backups, DR, límites de cuota y rate limiting
  • Alertas (SRE): latencia p95/p99, saturación, 5xx
  • Costos bajo control (requests/limits, namespaces)

Conclusiones

  • Atributos de calidad definen el éxito del sistema
  • Microservicios mejoran escalabilidad, pero aumentan complejidad
  • La malla de servicios facilita seguridad y observabilidad
  • CI/CD acelera la entrega confiable de software
